# S3 Backup boundary compatibility

The live default `AWSBackupServiceRolePolicyForS3Backup` version v5 adds only `s3:ListTagsForResource` compared with v4. The change reads bucket tags; the existing boundary was written against the earlier action set. Applying it unchanged would omit a permission AWS Backup now requests.

The boundary permits this one additional read action on the exact platform log and state bucket ARNs, conditioned on `aws:ResourceAccount` equaling the configured account. It does not grant tag writes, foreign service access, cross-account access, IAM authority or a new resource wildcard. All existing boundary statements, KMS alias/ViaService conditions and replication policies remain unchanged. The test and prod boundary documents are each 2613 characters, below the 6144-character managed policy limit.

[AWS's S3 API reference](https://docs.aws.amazon.com/AmazonS3/latest/API/API_control_ListTagsForResource.html) documents `s3:ListTagsForResource` for general purpose buckets. The cached [managed policy page](https://docs.aws.amazon.com/aws-managed-policy/latest/reference/AWSBackupServiceRolePolicyForS3Backup.html) still showed v4 during review; the live IAM GetPolicyVersion v4/v5 responses, rather than that stale version label, establish the exact current action delta.

The test metadata review identifies the canonical `s3-backup-role-ac43c65` selection as only `company-central-logs-eu-central-1-test` and `pulumi-bootstrap-infrastructure-test-state`. The older API-gateway selection belongs to `s3BackupServiceRole-f17edeb`; it is not added to this boundary. Sampled source-object encryption was AES256. This sample does not establish encryption for every historical object version, and a policy simulator cannot prove a completed real backup or restore.

Validation: both current-account boundary documents passed AWS Access Analyzer with no findings. There were 117 passing explicit-context effective-permission decisions using the actual canonical role's inline policy plus AWS managed v5 policy intersected with the proposed boundary. Cases cover selected and foreign buckets, new tag-read positive/negative ownership, existing bucket/object reads, tag mutation denial, actual KMS aliases with S3 service context, foreign key/account denial, and IAM escalation denial. The affected module has 214 statements and 70 branches at 100% coverage across 232 focused tests; all 117 policy tests pass.

Two exploratory simulator requests (four decisions) without an explicit `aws:ResourceAccount` ContextEntry were nondiagnostic: the engine allowed the named buckets even when ResourceOwner was overridden. Both initial reports, including the failed expectations, are retained. No missing-context or inferred-owner denial is claimed. The [SimulateCustomPolicy API documentation](https://docs.aws.amazon.com/IAM/latest/APIReference/API_SimulateCustomPolicy.html) distinguishes explicit context, resource-owner defaults and unsupported role resource-policy simulation. Production readiness still requires actual protected operator deployment and the relevant real backup/restore evidence.

Changing the boundary invalidates the previous operator saved plan. Review and generate a fresh plan before updating the policy, then generate a fresh platform plan before attaching it to the canonical backup role. This code change does not execute those updates or alter backup selections.
